## 1. プロジェクト概要

**優先度：P2 — 全体像を把握するための導入。**

PLU は PlayLoad を基盤とする JavaScript 製の小型ゲーム制作・実行環境である。ゲームのソースコードを圧縮して URL のハッシュに格納し、その URL を共有することで同じゲームを開ける構成を採る。

現在のリポジトリは PlayLoad のフォークであり、主要な実装は次の三領域に分かれる。

- ゲームエンジン: 画面・文字パターン・入力・サウンドの状態と更新を管理する。
- アプリケーション: エディター、ゲーム実行制御、入力 UI、画面表示、録画・保存を担当する。
- サイト／Arcade: 紹介ページと投稿作品一覧を生成・表示する。

### 現行の基本仕様

| 項目 | 実装 |
| --- | --- |
| 実行言語 | JavaScript (ES Modules) |
| 描画領域 | 160 × 144 ピクセル |
| 色 | 8 色のパレットインデックス |
| 文字・スプライト単位 | 8 × 8 ピクセル |
| 文字画面 | 20 列 × 18 行 |
| ゲーム更新 | 60 Hz を基準とする |
| 入力 | 上下左右、A・B の計 6 入力 |
| 音声 | 3 チャンネルの AY 系サウンド |
| 共有データ | JavaScript ソースを deflate-raw + Base64URL で URL に格納 |
| 新規共有サイズ上限 | 圧縮後 3000 bytes |
| 展開後ソース上限 | 1 MiB |

数値・制限の根拠は `src/engine/engine.js`、`src/payload.js`、`docs/design.md` と対応テストにある。

## 3. システム構成と実行境界

**優先度：P0 — 実行分離・メッセージ境界の中核。**

### 3.1 全体構成

通常のゲーム実行は、概ね次の経路を通る。

1. `main.js` が編集内容または URL のペイロードを受け取る。
2. `Runtime` が `GameSandbox` を生成する。
3. `GameSandbox` が `sandbox="allow-scripts"` の iframe を作成する。iframe は不透明オリジンで動作する。
4. iframe 内の `game-host.js` がゲーム Worker を起動する。
5. `game-worker.js` が `createEngine()` を作り、ゲームソースを関数本体として評価する。
6. Worker はゲーム更新後の 160×144 のピクセル配列とサウンド命令を親側へ返す。
7. `Runtime` と `Playback` が応答を検証・処理し、画面・音声へ反映する。

UI とゲームコードは同じ実行スレッドではない。ゲームが応答しなくなった場合、Runtime は監視タイマーで検出し、Worker を終了できる。

### 3.2 iframe と Worker の役割

- iframe はゲーム実行専用の境界を作る。不透明オリジン、`no-referrer`、制限された Content Security Policy を使用する。
- Worker はゲームコードを UI スレッドから分離し、フレーム単位で処理する。
- `game-host.js` は iframe と Worker の間に位置し、メッセージを中継する。
- ゲーム Worker はゲームから任意のメッセージを親へ直接送る経路を公開せず、内部の MessagePort をクロージャ内に保持する。
- メッセージは `game-messages.js` で形式、ピクセル配列、色範囲、サウンド命令などを検証する。

この構成は UI の停止を避けるための実行分離であり、あらゆる悪意あるコードに対する完全なセキュリティ保証を意味しない。

### 3.3 現在のネットワーク・外部データ境界

ビルドで生成される sandbox 文書の CSP は `default-src 'none'`、`connect-src 'none'` を含む。ゲーム Worker は data URL から起動されるバンドルであり、ゲームコード向けに外部データ取得 API を提供する実装は、今回確認したコードには存在しない。

したがって、外部データ読み込みやゲームからのネットワーク通信は現行機能として記載しない。将来追加する場合は、ホスト側の取得、Worker への受け渡し、信頼境界、サイズ制限、エラー処理、CSP を合わせて設計する必要がある。

## 4. ゲームエンジンと描画経路

**優先度：P0 — ゲームの実行結果と表示を決める中核。**

### 4.1 エンジン内部

`createEngine()` は 160×144 = 23,040 要素の `Uint8Array` をピクセル面として保持する。各要素は 0〜7 のパレット番号である。

文字画面は 20×18 セルで構成され、各セルは文字と前景色・背景色を保持する。文字の字形は 8 行の 8-bit パターンとして管理される。スプライトは毎フレームの一時描画リストとして保持される。

### 4.2 描画処理

1. 文字画面の各セルについて、文字パターンを 8×8 ピクセルへ展開する。
2. そのフレームのスプライトを重ねる。
3. 描画結果をパレット番号のピクセル配列として返す。
4. アプリ側の表示層が Canvas に反映する。

ゲームコードが画面の Canvas へ直接描く構造ではない。ゲーム API の描画命令はエンジン内のピクセル配列へ反映され、Canvas はアプリ側の出力先である。

### 4.3 Canvas 表示

- 通常表示: `display.js` が 8 色のパレットを RGBA に変換し、最近傍拡大した `ImageData` をメイン Canvas へ `putImageData()` する。
- CRT 表示: `crt.js` が別の WebGL Canvas で CRT シェーダーを適用し、メイン Canvas へ `drawImage()` する。
- 撮影: `capture.js` がメイン Canvas の `captureStream(60)` を使い、対応時は音声ストリームも合成する。
- スクリーンショット: メイン Canvas を画像 Blob として保存する。

このため、描画機能を拡張する場合も、既存のピクセル面へ描画結果を統合する方式が、CRT・録画・スクリーンショットとの整合性を保ちやすい。ただし、追加の図形描画 API は現時点では実装されていない。

### 4.4 既存の描画上限

`docs/design.md` とエンジン実装では、スプライト数、PCG 書き込み量、変更可能な文字種類に上限がある。超過時はグリッチ表現が発生する。詳細値や計数方法を変更する際は、設計文書と `tests/engine.test.js` 等の対応テストを同時に確認する。

## 5. 入力・時間・再生制御

**優先度：P1 — 操作とフレーム進行に直結。**

- 入力は上下左右・A・B の 6 ビットマスクとして扱う。
- アプリはキーボード、タッチボタン、標準マッピングのゲームパッドから入力を集約する。
- エンジンは現在押されている状態と、新たに押された瞬間の状態を管理する。
- `Playback` は requestAnimationFrame を基準に 60 Hz の進行を調整し、短い遅延は最大 5 ステップまで追いつき、長い停止時間は無制限に追いつかない。
- ページ非表示、ユーザーによる一時停止、画面切替などに応じて更新・音声・録画を同期する。
- Runtime は起動時 5000 ms、通常フレーム 1500 ms の応答監視を行う。フレーム要求は最大 5 ステップに制限される。

## 6. サウンド構成

**優先度：P2 — 主要機能の一つ。音声系変更時に確認。**

- `src/engine/sound.js` は ZX 128 PLAY 形式の文字列を解析し、イベント列へ変換する。
- AY クラスが 3 チャンネルの音声を生成する。矩形波、ノイズ、エンベロープ等を処理する。
- アプリ側の `Sound` は AudioContext と AudioWorklet を初期化し、音声処理をメイン UI から分離する。
- `Playback` がゲームフレームから届いたサウンド命令を音声側へ渡す。
- 録画時は利用可能な音声トラックを Canvas の映像ストリームへ追加する。

## 7. ペイロードと URL

**優先度：P0 — 保存・共有・旧 URL 互換性に直結。**

### 7.1 エンコード

`src/payload.js` はゲームソースを UTF-8 化し、CompressionStream の `deflate-raw` で圧縮する。圧縮バイト列をパディングなし Base64URL に変換し、`#v1.` を付けて URL ハッシュに格納する。

### 7.2 デコードと互換性

- 新形式 `#v1.` を読み込む。
- 旧形式 `#1.` も読み込む。
- 新規共有の圧縮上限は 3000 bytes。
- 旧 URL の読み込みは 3072 bytes まで許容する。
- 展開後のソースは 1 MiB まで。
- 不正な Base64URL、圧縮データ、UTF-8、過大な展開結果はエラーにする。
- URL の共有先向け長さ判定は 4096 文字を基準とし、プロトコル分の補正を行う。
- `gameURL()` は検索パラメータを除き、ゲームのハッシュを設定する。

### 7.3 URL がゲーム本体を兼ねる

ゲームのソースは URL ハッシュ内に格納される。保存・共有は URL のブックマークまたは URL の送信を基本とする。サーバー側のゲームデータベースを前提としない。

### 10.2 ビルド処理

`scripts/build.js` は esbuild でアプリ、サイト、Arcade、スタイル、Worker をバンドルする。テンプレートへ生成値を埋め込み、`dist/playload/` 以下に公開用ファイルを構築する。Worker はビルド時にバンドルされ、sandbox のホストスクリプトへ埋め込まれる。sandbox 文書には生成した CSP が設定される。

ビルドは一時ディレクトリに生成してから出力先を置き換える。出力先がリポジトリ内の許可されない場所やソースを上書きする場所にならないよう検査する。

### 10.3 GitHub Pages

`.github/workflows/deploy-pages.yml` は `main` と `plu/gem-survivor-preset` への push、および手動実行でビルドジョブを開始する。成果物は `dist/playload`。デプロイジョブは `main` ブランチの場合に限り実行される。

`package.json` の homepage は `https://lvlatsu.github.io/playload/` で、ビルドは公開パス `/playload/` を前提にしている。

### 10.4 Wrangler 設定上の注意

`wrangler.jsonc` には `kitao.dev/playload*` の Cloudflare Workers ルートが記載されている。これはフォーク元由来の設定を含む可能性があり、GitHub Pages の公開設定とは別系統である。Cloudflare へのデプロイを実行する場合は、対象ドメイン・アカウント・権限・公開先を必ず確認する。現状のコード調査だけでは Cloudflare へのデプロイ実績を示さない。

## 13. 変更時の基本ルール

**優先度：P0 — 互換性・安全性・品質を守る共通ルール。**

1. 変更対象の責務を持つファイルを特定し、隣接するテストを確認する。
2. API の変更は既存 API リファレンスと互換性への影響を別途確認する。
3. 生成物は生成元・生成スクリプトから更新する。
4. Worker 境界の変更はホストと Worker の両側で検証する。
5. 描画変更は通常表示、CRT、録画、スクリーンショットを含めて確認する。
6. ペイロード変更は新旧 URL、圧縮上限、URL 長、展開後上限を確認する。
7. 公開設定変更は GitHub Pages と Wrangler を混同せず、公開先を確認する。
8. 実行していないテストや実機確認を、完了済みとして記録しない。
