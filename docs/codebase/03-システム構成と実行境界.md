## 3. システム構成と実行境界

**優先度：P0 — 実行分離・メッセージ境界の中核。**

### 3.1 全体構成

通常のゲーム実行は、概ね次の経路を通る。

1. `main.js` が編集内容または URL のペイロードを受け取る。
2. `Runtime` が `GameSandbox` を生成する。
3. `GameSandbox` が `sandbox="allow-scripts"` の iframe を作成する。iframe は不透明オリジンで動作する。
4. iframe 内の `game-host.js` がゲーム Worker を起動する。
5. `game-worker.js` が `createEngine()` を作り、ゲームソースを関数本体として評価する。
6. Worker はゲーム更新後の 160×144 のピクセル配列とサウンド命令を親側へ返す。
7. `Runtime` と `Playback` が応答を検証・処理し、画面・音声へ反映する。

UI とゲームコードは同じ実行スレッドではない。ゲームが応答しなくなった場合、Runtime は監視タイマーで検出し、Worker を終了できる。

### 3.2 iframe と Worker の役割

- iframe はゲーム実行専用の境界を作る。不透明オリジン、`no-referrer`、制限された Content Security Policy を使用する。
- Worker はゲームコードを UI スレッドから分離し、フレーム単位で処理する。
- `game-host.js` は iframe と Worker の間に位置し、メッセージを中継する。
- ゲーム Worker はゲームから任意のメッセージを親へ直接送る経路を公開せず、内部の MessagePort をクロージャ内に保持する。
- メッセージは `game-messages.js` で形式、ピクセル配列、色範囲、サウンド命令などを検証する。

この構成は UI の停止を避けるための実行分離であり、あらゆる悪意あるコードに対する完全なセキュリティ保証を意味しない。

### 3.3 現在のネットワーク・外部データ境界

ビルドで生成される sandbox 文書の CSP は `default-src 'none'`、`connect-src 'none'` を含む。ゲーム Worker は data URL から起動されるバンドルであり、ゲームコード向けに外部データ取得 API を提供する実装は、今回確認したコードには存在しない。

したがって、外部データ読み込みやゲームからのネットワーク通信は現行機能として記載しない。将来追加する場合は、ホスト側の取得、Worker への受け渡し、信頼境界、サイズ制限、エラー処理、CSP を合わせて設計する必要がある。
