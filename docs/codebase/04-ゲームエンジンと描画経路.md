## 4. ゲームエンジンと描画経路

**優先度：P0 — ゲームの実行結果と表示を決める中核。**

### 4.1 エンジン内部

`createEngine()` は 160×144 = 23,040 要素の `Uint8Array` をピクセル面として保持する。各要素は 0〜7 のパレット番号である。

文字画面は 20×18 セルで構成され、各セルは文字と前景色・背景色を保持する。文字の字形は 8 行の 8-bit パターンとして管理される。通常スプライトと基本図形、BG・MG・FG の描画命令はフレーム単位のキューに登録される。

### 4.2 描画 API と合成順

現行の描画 API は次のとおり。

- 既存 API：`cls()`、`put()`、`spr()`、`scr`、`pcg`
- PLU 基本図形 API：`upix()`、`ulin()`、`urec()`、`uelp()`
- レイヤー：`BG`、`MG`、`FG`。各レイヤーで `spr()` と4種類の基本図形 API を利用できる。

描画時の合成順は次のとおり。

1. 文字画面（`scr` / `put()` / `cls()`）
2. 通常の `spr()` と通常の基本図形 API
3. BG レイヤー
4. MG レイヤー
5. FG レイヤー

BG・MG・FG は固定順で合成する。各レイヤーの命令は毎フレーム初期化されるため、表示を継続するには毎フレーム `tick()` から登録する。各描画キューには1フレーム最大128命令の上限がある。

基本図形 API の引数・座標・塗りつぶし・クリッピング規則は [`17-基本図形描画API仕様案.md`](17-基本図形描画API仕様案.md)、レイヤーの詳細は [`18-BG-MG-FGレイヤー描画.md`](18-BG-MG-FGレイヤー描画.md) を参照する。

### 4.3 Canvas 表示

- 通常表示：`display.js` が8色の RGB パレットを使い、ピクセル面を RGBA に変換してメイン Canvas へ反映する。
- CRT 表示：`crt.js` が別の WebGL Canvas で CRT シェーダーを適用する。実行時パレット変更にも対応する。
- 撮影：`capture.js` がメイン Canvas の `captureStream(60)` を使い、対応時は音声ストリームも合成する。
- スクリーンショット：メイン Canvas を画像 Blob として保存する。

ゲームコードが Canvas や WebGL へ直接描画する構造ではない。描画 API の命令はエンジン内のピクセル面へ統合され、既存の表示・CRT・録画・スクリーンショット経路を通る。

### 4.4 実行時パレット

`ucpl.set()` / `setAll()` / `get()` / `reset()` により、ゲーム実行中に8色の RGB 値を変更・取得・復元できる。ピクセル面は色番号を保持し、RGB 値は表示側で参照する。Worker からホストへパレット情報を渡し、通常表示と CRT 表示へ反映する。

詳細は [`20-実行時カラーパレットAPI仕様案.md`](20-実行時カラーパレットAPI仕様案.md) を参照する。

### 4.5 制約と確認状態

- 画面外の図形は画面内へクリッピングする。図形描画はアンチエイリアスなしの整数ドット方式。
- 各フレームの描画キュー上限は128命令。上限超過時は既存のグリッチ通知方式を使う。
- 自動テストは `tests/engine.test.js` 等に存在する。ただし、仕様書更新時点でテストスイートを実行したことを意味しない。
- 最新のブラウザ・Android 実機確認は別途記録する。実装済み、テストコードあり、テスト実行済み、実機確認済みを混同しない。
