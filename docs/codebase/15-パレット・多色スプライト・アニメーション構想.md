# PLU 描画拡張構想 — パレット・多色スプライト・アニメーション

> この章は、2026-11-19 の設計会話で出た将来構想を記録するものです。ここに記載する API 名・引数・データ形式は、確定仕様でも実装済み機能でもありません。既存 PlayLoad との互換性、エンジン構造、実装コストを確認してから正式決定します。

## 1. 目的

PLU の描画機能を、既存の 8×8 字形・単色スプライト中心の仕組みから段階的に拡張する。

- 色番号と実際の RGB 色を分離し、ゲーム実行中にパレットを変更できる。
- グラフィック側の色割り当て・パレット情報も、内部データ構造を直接操作せず API 経由で扱えるようにする。
- 1 枚のスプライトを複数色で構成できるようにする。
- スプライトやエフェクト、パレットなどを時間軸に沿ってアニメーションさせる。
- 将来的に「．えでぃ太」で制作した多色画像・アニメーションを PLU で利用できるようにする。

既存の put() / spr() / pcg は互換性を維持し、拡張機能で置き換えない方針を基本とする。

## 2. パレット機能の階層

パレット関連は、少なくとも次の2つの役割に分けて考える。

### 2.1 グラフィック側のパレット情報

グラフィックやスプライトのデータが、どの色番号を使うかを管理する層。

- 現行 pcg[chr].col は、文字パターンの前景色・背景色を指定する。
- 将来は、グラフィック側の色割り当てやパレット参照を API 化し、pcg の内部構造をゲームコードから直接操作しなくてもよい形を検討する。
- API 名候補：ugpl()（Unlimited Graphic Palette）。名称・対象範囲・引数は未確定。
- 多色スプライトでは各ドットが色番号を持つため、従来の前景色・背景色ペアだけで十分かを再検討する。

### 2.2 実 RGB カラーパレット

色番号に対応する実際の RGB 値を管理する層。

- API 名候補：ucpl()（Unlimited Color Palette）。
- 例：ucpl(1, 0xff0000) は、色番号1に対応する RGB 色を赤へ変更するイメージ。
- 色番号は既存のパレット番号との互換性を考慮する。
- パレットを変更したとき、すでに画面に描画されている同じ色番号のピクセルも新しい RGB 色で表示されることを想定する。
- 標準パレットへの復元、一括設定、範囲外の色番号や不正な RGB 値の扱いを定義する必要がある。

ugpl() は「グラフィックがどの色番号を使うか」、ucpl() は「その色番号を実際に何色で表示するか」という役割分担を想定する。両者の正式な責務は、多色スプライトのデータ形式と合わせて決定する。

## 3. 多色スプライト

### 3.1 目標

従来の spr() は互換性のために残し、新しい形式では1枚のスプライト内に複数のパレット番号を持てるようにする。

例えば、1枚の画像の中で黒・赤・黄・青などを同時に使える。これにより、キャラクター、敵、アイテム、背景パーツ、エフェクトなどを、複数の単色スプライトへ分割せずに表現できる。

### 3.2 データ形式の検討事項

- 各ピクセルがパレット番号を持つ方式を基本候補とする。
- 透明は既存の色番号を流用せず、パレット色と区別できる表現を設ける。透明値・マスク・アルファのどれを採用するかは未決定。
- 8×8 の既存字形との互換性、および将来の任意サイズ画像との関係を整理する。
- パレット変更で多色スプライトの色も一括変更できる構造にする。
- 画像データの登録・更新・描画 API と、データ容量・書き込み予算・描画負荷を定義する。

### 3.3 既存 API との関係

- spr() の動作・引数・既存作品の表示結果は変えない。
- 多色スプライトは別のデータ形式・API として追加する方向。
- 既存 pcg.pat / pcg.col と多色画像データをどのように共存させるかを設計する。
- Canvas へ直接描かず、エンジン内部のピクセル面へ反映し、通常表示・CRT・録画・スクリーンショットの経路を維持する。

## 4. アニメーション機能

### 4.1 対象

アニメーションはスプライトのフレーム切り替えだけに限定しない。

- キャラクターの歩行・攻撃・ダメージ・待機
- 爆発・ヒット・煙などのエフェクト
- 炎・水面など環境表現
- パレット切り替えによる点滅・色変化・時間帯表現
- 将来的には背景や画面効果など

### 4.2 基本構想

アニメーションデータを登録し、ゲーム本体は再生・停止・表示などを指示する方式を検討する。フレーム番号、フレーム表示時間、ループ、再生方向、終了時の扱いなどを定義する。

ゲーム本体の毎フレーム処理にアニメーション切り替え処理を大量に書かなくてもよいよう、エンジン側で時間管理できる設計を目指す。

### 4.3 API 名の候補

過去の会話で出た仮案：

| 候補 | 想定する役割 | 状態 |
| --- | --- | --- |
| uani() | アニメーション定義・登録 | 仮案 |
| ufrm() | フレーム指定・切り替え | 仮案 |
| uasp() | アニメーションスプライト表示 | 仮案 |

この3つの分担が最適とは限らない。定義・再生制御・描画をどこまで分離するかを決め、既存 API や上流 PlayLoad の将来 API と名前が衝突しないことを確認してから確定する。

### 4.4 点滅・明滅

点滅は独立した特殊機能にせず、アニメーションの一種として扱う方向で検討する。

- 表示／非表示を交互に切り替える点滅（無敵時間・警告表示など）。
- パレット番号や RGB 色を切り替える色点滅（被ダメージ・状態変化など）。
- 明るさや色味を周期的に変える脈動表現（発光・魔法効果など）。
- 特定の色だけを切り替える部分的な点滅。
- 周期・速度・開始／停止をゲーム側から制御できるようにする。

画像フレームを切り替えなくても、表示状態やパレットを時間変化させることで実現できる。点滅頻度や視認性にも配慮し、強い高速点滅を常用しない設計とする。

### 4.5 スプライトの変形・変換

アニメーションと組み合わせる将来機能として、描画時のスプライト変換を検討する。

- 拡大・縮小（倍率指定）。
- 回転（角度指定）。
- 左右反転・上下反転。
- 倍率や角度を時間変化させる変形アニメーション。
- 必要に応じて、変換後の描画位置・基準点（アンカー）を指定する。

回転・拡大縮小はフレーム切り替えとは異なり、スプライトの描画処理そのものに関わる。補間方式、回転中心、ピクセルのにじみを避ける描画方式、画面外クリッピング、処理負荷を別途設計する。既存 spr() の挙動は変更せず、必要なら拡張 API として追加する。

API 名・引数は未定。変換機能をアニメーション機構に内包するか、描画 API として独立させるかも今後決定する。

## 5. ．えでぃ太との連携

将来の制作フローとして、次を目指す。

1. ．えでぃ太で多色ドット絵を制作する。
2. 必要に応じて複数フレームを作成し、アニメーションを編集する。
3. PLU が読み込める形式でデータを出力する。
4. ゲーム側でアセットを登録し、スプライトやアニメーションとして利用する。

エディターとの直接連携や転送方式は未実装。まずはデータ形式を共通化し、テキスト出力・ペイロード取り込みなど既存の共有方式と整合する方法を検討する。

## 6. 設計・実装前に決めること

1. ucpl() の色番号範囲、RGB 表現、初期パレット、復元・一括設定の仕様。
2. ugpl() が管理する対象（字形単位、画像単位、スプライト単位、または共通の色割り当てデータ）。
3. 多色スプライトのサイズ、色深度、透明表現、データ登録・描画方法。
4. 既存 pcg / spr() との互換性と共存方法。
5. アニメーションのフレーム構造、時間単位、ループ・停止・再生制御。
6. パレットアニメーションと画像フレームアニメーションを共通の仕組みで扱うか、分けるか。
7. データ容量、ペイロードサイズ、メモリ、書き込み予算、フレーム負荷の上限。
8. エディターから出力するデータ形式と PLU 側の読み込み方式。
9. API 名の衝突確認、公開 API リファレンス・テストの更新方針。
