## 1. 最初に読むこと

PLU は PlayLoad をフォークし、独自のゲーム制作・実行環境へ発展させるプロジェクトです。既存の PlayLoad との互換性を尊重しながら、ゲーム作者がより豊かな表現を簡潔に実現できる基盤を整えます。

このプロジェクトは、特定のゲームを完成させるためだけのものではありません。GEM SURVIVOR は開発のきっかけであり、サンプル作品です。PLU 本体の目標は、さまざまな制作者が自由に挑戦できる制作・実行環境を育てることです。

開発史は [`PLU_HISTORY.md`](PLU_HISTORY.md)、設計判断と作業履歴は [`PLU_DEVLOG.md`](PLU_DEVLOG.md) を参照してください。

## 2. 現在の到達点

ソース機能の棚卸しは `a7e1f7fc233a0e9980f0f855d054b6ddcf5d9cdb`（2026-11-20）を基準に行いました。その後、`7dbe764932b132fc84fbd9286f81ec7b580439c2` で STAR FLOW の生成済みメタデータにあった重複キーを修正しています。現行 main の実装確認は、以降のコミットも含めて継続してください。

基準コミット時点で、ソース上に次の機能を確認しています。

- PlayLoad を基盤とするゲームエンジン、エディター、ゲーム実行環境
- iframe / Worker を使ったゲーム実行の分離
- URL ハッシュを使ったゲームソースの圧縮・共有
- 160×144 ピクセル、8色パレット、20×18文字セルの画面
- 既存の `cls` / `put` / `spr` / `scr` / `pcg` API
- PLU 独自の基本図形 API：`upix` / `ulin` / `urec` / `uelp`
- BG / MG / FG の3レイヤー。各レイヤーでスプライトと基本図形を描画可能
- 実行時 RGB パレット API：`ucpl.set` / `setAll` / `get` / `reset`
- 数学 API：`urnd` / `usin` / `ucos` / `utan` / `usqr` / `uabs` / `uflr` / `ucei` / `umin` / `umax` / `upow` / `uatan2`
- 通常表示、CRT 表示、録画、スクリーンショットの既存経路

上記はコード上の実装確認です。最新のテスト成功、Android 実機での動作、公開サイトへの反映を保証するものではありません。

### 3.2 テスト

関連する自動テストコードはリポジトリにあります。ただし、上記の調査・文書更新作業ではテストを実行していません。

`package.json` の主なコマンド：

| コマンド | 内容 |
| --- | --- |
| `npm test` | Node.js の単体テスト |
| `npm run test:browser` | Playwright ブラウザテスト |
| `npm run check` | lint、整形確認、生成物確認、単体・参照・ブラウザテスト |
| `npm run build` | 公開用サイトのビルド |

Node.js の要求バージョンは `>=24`。依存関係を導入する場合は `npm ci` を使います。

## 6. 情報の優先順位

記録が食い違った場合は、次の順で確認します。

1. **現行ソースコード**：実際に何が実装されているか。
2. **公開 API リファレンス（`data/reference.json`）**：ゲーム作者へ公開している API 名・使い方。
3. **自動テストコード**：期待する挙動や境界条件。ただしテストコードの存在だけでは実行成功を意味しない。
4. **確定仕様書**：合意した仕様・制約・設計理由。
5. **ロードマップ・構想資料**：今後の候補。実装済みと解釈しない。
6. **過去の会話・開発日誌**：決定の背景や経緯を補う資料。

矛盾を見つけたら、古い文書を推測で書き換えず、まずソース・API リファレンス・テストを照合してから更新します。

## 7. 変更作業の標準手順

1. 現在の main と対象コミットを確認する。
2. 変更対象のソース、関連仕様書、API リファレンス、テストを読む。
3. 変更目的、変更範囲、非対象、受け入れ条件を明確にする。
4. 必要なファイルだけを変更する。
5. 対応テストを追加・更新し、実行する。
6. API リファレンスと関連仕様書を更新する。
7. 開発記録に「何を・なぜ・どのコミットで変更したか」を残す。
8. テスト結果、実機確認、ビルド、デプロイを別々に記録する。
9. 次の担当者が再開できるよう、残課題と次の作業を更新する。

### 完了報告で必ず分ける項目

- ソース実装：変更したか
- テストコード：追加・更新したか
- テスト実行：何を実行し、成功・失敗したか
- ブラウザ／実機：どの環境で確認したか
- ビルド：成功したか
- デプロイ：成功したか
- 公開先：実際に新しい内容が見えることを確認したか

「実装した」だけで「動作確認済み」「公開済み」と書かないでください。

## 8. 開発環境・作業上の配慮

主な開発作業は Android スマートフォン上のブラウザを使って進められてきました。担当者が PC の IDE や GitHub の複雑な操作に慣れているとは限りません。

- 変更案内は、スマートフォンでも追いやすい短い手順にする。
- コード変更を人へ依頼する場合、断片的な差分ではなく、変更対象ファイルの完全な内容を提示する。
- 不要なファイルを変更しない。
- GitHub の操作や確認方法は、実際の画面・操作に沿って説明する。
- 実行していない作業を実行済みと伝えない。

## 9. プロジェクトの大切な前提

- PLU は PlayLoad のフォークを出発点とする独自発展プロジェクト。
- 既存作品との互換性を大切にする。
- 基盤 API は、特定のサンプルだけでなく多様な作品に役立つかを考えて設計する。
- 先に大きな機能を足すより、既存 API の一貫性・検証・記録を固める。
- 仕様、実装、テスト、検証、公開の状態を分けて記録する。
- 過去の設計理由を残し、担当者が変わっても判断の根拠を追えるようにする。
